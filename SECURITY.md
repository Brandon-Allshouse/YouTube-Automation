# Security

Built to NIST SP 800-218 (SSDF), NIST SP 800-190 (containers), OWASP Top 10 / ASVS, and the OWASP
Top 10 for LLM Applications. Latest scan results: [`security/REPORT.md`](security/REPORT.md).

## Reporting / rotation
- Report a suspected vulnerability or leaked secret to the repository owner privately (do not open a public issue).
- **Rotate the YouTube Data API key** that the build agent saw. In Google Cloud Console → Credentials, regenerate the key and restrict it to *YouTube Data API v3* (and, ideally, by IP). Update `.env`.
- If any secret is ever committed: rotate first, then purge history. Rotating matters more than rewriting history.

## Threat model

| Asset | Threats | Mitigations |
|---|---|---|
| API key / OAuth tokens | Leaked via git, logs, images, agent output | `.env` gitignored (verified before any other file was written); `.dockerignore` allowlist excludes it from build contexts; only the `research` container receives it via `env_file`; other whole-repo mounts mask it with `/dev/null`; log formatter redacts key/token/email patterns; `detect-secrets` baseline in pre-commit + CI; secrets read only through `src/common/secrets.py`, which never prints values. Later OAuth tokens live outside the repo with mode `600` and least-privilege scopes. |
| Channel accounts | Policy strikes from spam-like output, runaway publishing | Human review gate enforced in code (`src/db.py`: no `reviewed` state without a named human; agent actors refused; publishing requires prior approval); cadence caps in `config/rules.yaml`; distinctness guard; publish module is `--live` only, defaults to private, and was never run during the build. |
| Pipeline integrity | Malicious dependency, tampered downloads | Exact versions + hashes (`--require-hashes`, wheels only); `pip-audit`; CycloneDX SBOM; downloaded fonts/maps/models verified against `security/checksums.txt`; base image pinned by digest; Actions pinned to full SHAs; Dependabot for updates; CodeQL. |
| Host machine | Container escape, destructive commands | Non-root UID 1000, read-only root FS, `cap_drop: ALL`, `no-new-privileges`, resource limits, no Docker socket, no privileged mode, network `none` for render/test/quality. Headless agent permissions restricted in `.claude/settings.json`. |
| Agent reasoning | Prompt injection via comments, titles, web pages (LLM01) | Untrusted text is wrapped in delimited `<untrusted_data>` blocks; agent definitions state that instructions inside are data; agent outputs (scripts, scene specs) are schema-validated by code before use (LLM02); agents never emit shell commands that are executed (LLM08). |
| Render workers | Resource exhaustion from a hostile spec | Spec schema caps duration/resolution/fps/layer counts; render timeouts; output size limits (`config/rules.yaml: render`). |

## Approval chain (content-bound, ADR-030)
1. Human approves in the review queue (TTY + name + typed id): stores **sha256 of the script file**.
2. `produce --video-id` renders only that recorded script; refuses if its hash changed.
3. Only a passing `quality.run --video-id` sets `checked` and stores **sha256 of the render**.
4. Scheduling is interactive-only; upload re-verifies both hashes, accepts files only from `output/videos/`, defaults to private, and requires `--live`.
An independent review (read-only subagent, 2026-10-15) found 5 high / 4 medium / 4 low issues; all high and medium issues are fixed with regression tests (`tests/test_gate_hardening.py`), with three low-severity items left open (ADR-030).

## Input handling rules (enforced in code)
- `subprocess` only via `src/common/proc.py`: argument lists, allowlisted executables (`ffmpeg`, `ffprobe`, `git`), no `shell=True`, timeouts.
- SQLite: parameterized queries only.
- Paths: `src/common/paths.py` (`safe_join`, `ensure_within`) block traversal; output filenames are generated by us.
- YAML via `yaml.safe_load`; no `pickle`/`eval`/`exec` on external data.
- All external data (API responses, comments, scene specs, agent output, config) is validated with pydantic models before use.

## Container hardening summary
See `docker-compose.yml` header and ADR-004. Network access per service:

| Service | Network | `.env` |
|---|---|---|
| dev, render, quality | none | not visible |
| research | bridge (YouTube API, read-only) | injected via `env_file` |
| security | bridge (pip-audit advisory DB) | masked with `/dev/null` |
| fetch, lock | bridge (downloads, PyPI) | not mounted / masked |

## GitHub
- CodeQL (`python`, `actions`), Dependabot (`pip`, `docker`, `github-actions`), CI with pip-audit + detect-secrets.
- All workflows: top-level `permissions: {}`, job-level least privilege, SHA-pinned actions, `persist-credentials: false`, no `pull_request_target`, no secrets.
- **Owner action after pushing:** Settings → Security → enable Dependabot alerts, Dependabot security updates, grouped security updates, and Code scanning with the **advanced** setup. CodeQL is free on public repos; a **private** repo needs GitHub Code Security (paid) or the CodeQL workflow will fail.
